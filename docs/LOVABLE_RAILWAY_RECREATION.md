# Billiken Lovable + Railway Recreation Guide

**Captured:** 2026-07-19

This is a preservation record of the public Lovable dashboard at
`https://billiken-projected-standings.lovable.app/`, its Railway backend at
`https://billiken-production.up.railway.app`, and the repository implementation
that supports them. It is intended to make a clean-room recreation possible in
another frontend host and/or deployment service.

## What exists

The public application is a single-page React dashboard. It has one route (`/`)
and three primary tabs:

1. **Standings** — live projected roto standings and per-team detail.
2. **Best Available** — sortable free-agent rankings.
3. **Trade Lab** — posture-aware trading suggestions plus a manual trade
   builder.

It does not contain authentication, user accounts, persisted client-side
settings, editing controls, or an automatic refresh button. React Query caches
requests in memory; the standings request polls every five minutes.

The source of truth is this repository. Railway runs `server.js`, which reads
processed CSV/JSON artifacts generated by R scripts. Lovable is only the
frontend and calls Railway directly over public HTTPS.

## Visual system and page shell

- Dark baseball-analysis theme: near-black/navy page background, green primary
  accent, sky-blue secondary accent, muted gray cards and borders, red errors,
  amber warnings, violet prospect tags, and sky-blue pick tags.
- Main display face: `Space Grotesk`; tabular numbers: `JetBrains Mono`.
- Layout: full-width page with a bordered header and a centered `max-width:
  80rem` content column; desktop padding is 24 px.
- Header: Billikens logo, **Billiken League**, subtitle **Fantasy Baseball
  Standings**, and an `Updated <local timestamp>` label when the standings
  payload includes `status.last_updated`.
- The supplied Lovable bundle references `/assets/billikens-logo-DhRFbElT.png`.
- The public deployment currently has the title *Billiken Fantasy Baseball
  League - Projected Standings* and the description *Season-to-date stats plus
  rest-of-season projections based on current rosters.*

Use responsive, horizontally scrollable tables. First columns are sticky for
team/player identity; tables use visible sort arrows, monospace numbers, and
hover row states. The Blue Socks row is specially highlighted blue with a left
border.

## Tab 1 — Standings

### Default behavior

On initial load, call `GET /inseason_standings`. Show a loading spinner until
it resolves and a full-page error state if it fails. Default sort is projected
rank ascending. The visible context label is **All rostered players** unless
the server supplies `view`.

The table contains:

| Column | Source / display |
| --- | --- |
| # | Current client-side sort order (not the server `projected_finish`) |
| Team | `team_name`; clicking opens team detail |
| Pts | `total_pts` |
| R, HR, RBI, SB, AVG, W, SV, SO, ERA, WHIP | `proj_<category>` on the first line and `pts_<category> pts` beneath |

All numeric headers except Team sort on click and reverse when clicked again.
Default direction is ascending for rank/ERA/WHIP and descending otherwise.
AVG is rendered to three decimals without the leading zero; ERA/WHIP to two;
integer-like category totals are rendered without decimals.

An **Active roster only** toggle refetches `GET /inseason_standings?active_only=true`.
It replaces the table, changes the context label to **Active roster only**, and
is also passed to the detail screen so non-active players appear faded and
struck through. The specific team request itself is unchanged.

### Stale/error notices

Render notices before the table when the returned `status` requires them:

- red error notice when `status.status === "error"`, using `error_message` if
  supplied;
- one amber notice for each `status.warnings[]` item;
- amber SGP fallback notice when `status.sgp_source === "fallback"`;
- amber stale notice when `last_updated` is more than 36 hours old.

### Team detail

Selecting a team hides the tabs and shows **Back to Standings**, the team name,
and two separate sortable tables.

| Section | Columns |
| --- | --- |
| Hitters | Player, Slot, Status, AB, H, R, HR, RBI, SB, AVG |
| Pitchers | Player, Slot, Status, IP, W, SV, SO, ERA, WHIP, ER, BB, HA |

The initial sort is Slot ascending. Hitter slots sort as C, 1B, 2B, 3B, SS, OF,
MI, CI, Util; pitchers all use slot `P`. Status badges are green Active, muted
Bench, red IL, and blue Minors. AVG is calculated as H/AB if absent. All table
headers sort, including text columns.

## Tab 2 — Best Available

This tab calls `GET /inseason_free_agents` with `type`, optional `position`,
and `limit=50`. Defaults are **Hitters**, position **All**, and sort **ROS SGP
descending**. Switching hitter/pitcher resets position and sort.

Controls:

- segmented **Hitters** / **Pitchers** switch;
- Position dropdown. Hitter choices: All, C, 1B, 2B, 3B, SS, OF, MI, CI, Util,
  DH. Pitcher choices: All, SP, RP.

The table has sticky Name and sortable #, Name, MLB Team, Positions, projected
stat categories, and ROS SGP. Positions render as separate small pills. Exact
stat columns are frontend-defined by hitter/pitcher type, so preserve the
current frontend column lists when recreating. It also shows the same data
status notices and a `Last updated <local timestamp>` footer when present.

## Tab 3 — Trade Lab

### Landing state

Fetch `GET /team_posture` and `GET /inseason_standings`. Default **My team** is
Blue Socks if available, otherwise the first posture row. A dropdown permits
any team. Present a large card for My team with its posture badge, projected
finish, projected points, gap to third, playoff probability, keeper metrics,
and buy/sell priority text.

Show all other teams as clickable cards, sorted by posture then projected
finish. Selecting one scrolls to the trade panel. Posture categories are
`contender`, `bubble`, `mid`, and `rebuild`; preserve the colour distinction
and explanatory legend.

### Suggested trades

When two teams are selected, call:

`GET /trade_targets/:my_team?partner=:partner&horizon=balanced`

For a rebuild user, request `horizon=future`, filter out `stretch` trades with
non-positive `my_future_delta`, and sort suggestions by future delta. For other
postures, use balanced sorting.

Each suggestion card shows:

- **You get** target player, asset-type badge, optional `stretch`/`fallback`
  badge, prospect rank/ETA/value or pick value/source metadata, and value to
  me;
- **You give** tokenized `proposed_offer` assets (top-level `|` separators;
  separators inside parentheses/brackets are retained);
- my and partner value deltas, including win-now and future signals where
  supplied;
- a **Load into builder** action that selects the proposed assets and scrolls
  to the builder.

The empty state says that there are no automated matches and directs the user
to build a trade below.

### Manual builder

The builder has a two-panel selector: **Partner · [name]** and **My Roster ·
[name]**. Each shows a searchable, fixed-height (520 px) roster table sorted
by `surplus_2026` descending. Rows are selectable checkboxes and show Player,
contract status/year, salary, value, surplus, total/future values, and asset
type (player/prospect). There is a Clear action.

Each asset with `future_value_breakdown` now has a disclosure chevron beside
its name. Expanding it inserts a compact, horizontal-scrollable **Future value
breakdown** table directly beneath the asset. Its rows are the future seasons
(currently 2027–2030) and its columns are **Season**, **Projection**,
**Prospect**, **Source**, **Selected**, **Salary**, **Net**, and
**Discounted**. The source is a coloured pill: projection (green), prospect
(violet), not-under-contract (slate), or muted fallback. Net and Discounted
use the positive/negative value colouring. This is a display-only drilldown;
the existing asset-selection and evaluation request are unchanged.

It also exposes each side's 2027 picks for rounds 1–7, rendered as dashed pick
rows. The client uses pick IDs in the canonical form `pick_YYYY_RNN`, e.g.
`pick_2027_R02`.

After each selection change, debounce 350 ms then call:

```json
POST /evaluate_trade
{
  "my_team": "<Billiken team identifier>",
  "partner_team": "<Billiken team identifier>",
  "my_asset_ids": ["Player Name", "pick_2027_R02"],
  "partner_asset_ids": ["Player Name"]
}
```

Show both sides' 2026 ROS net and future/keeper net, large team-named
**[Team] Weighted Net** values, the weighting explanation, and returned
guidance. This action is read-only: it does not create or execute a league
transaction.

## Railway contract

### Runtime and deployment

- Entrypoint: `server.js` (Hono; Bun runtime).
- Container: [`Dockerfile`](../Dockerfile), based on `rocker/r-ver:4.4.1`,
  installs Bun and R dependencies through `renv::restore()`, then starts the
  API service.
- CORS permits any origin and GET/POST/OPTIONS with `Content-Type`.
- No endpoint authentication exists. Do not expose simulation-triggering POST
  endpoints publicly in a recreated production deployment without adding auth.
- Railway needs the R runtime, `renv.lock` dependencies, processed-data volume
  or scheduled regeneration, plus the environment variables described in
  [`WARP.md`](../WARP.md).

### Endpoints used by the Lovable dashboard

| Endpoint | Method | Response property used | Notes |
| --- | --- | --- | --- |
| `/inseason_standings[?active_only=true]` | GET | `standings`, `status`, optional `view` | Main standings. |
| `/inseason_team/:team` | GET | `players` | Team detail; backend matches team substring case-insensitively. |
| `/inseason_free_agents?type=&position=&limit=50` | GET | `free_agents`, `status` | Best Available source. |
| `/team_posture` | GET | `team_posture` | Trade Lab teams and posture. |
| `/team_assets/:team` | GET | `players`, `count` | Trade-builder roster assets. |
| `/draft_pick_values?team=:team` | GET | `picks` | 2027 pick selector. |
| `/trade_targets/:my_team?partner=&horizon=` | GET | `trades` | Automated offers. |
| `/evaluate_trade` | POST | nets, side totals, guidance | Manual trade evaluation. |

Useful supporting endpoints are `/health`, `/inseason_status`,
`/team_assets`, `/team_keeper_pressure`, `/prospect_values`, and
`/inseason_pt_benchmarks`.

### Important response fields

The schemas are intentionally data-driven CSV-to-JSON objects. Preserve nulls;
the backend explicitly avoids turning empty CSV cells into zero.

- Standings: `team_name`, `projected_finish`, `total_pts`, `proj_*`, `pts_*`,
  `rank_*`, and pairing counts.
- Team player: `player_name`, `player_type`, `lineup_slot`, `roster_status`,
  season/projection statistics.
- Free agent: `Name`, `Team`, `positions`, `player_type`, `rank_by_type`,
  stat fields, and `sgp_total`.
- Team posture: `team_name`, `billikenTeam`, `posture`, `proj_finish`,
  `proj_total_pts`, `gap_to_third`, `gap_to_first`, `playoff_prob_top3`, keeper
  counts, `priority_buy`, and `priority_sell`.
- Team asset: `Name`, `player_type`, `positions`, `roster_status`, salary and
  contract fields, `dashboard_value_2026`, `surplus_2026`, `win_now_value`,
  `future_value`, prospect metadata, and `future_value_breakdown`. Each
  breakdown row has `season`, `projection_value`, `prospect_value`,
  `selected_source`, `selected_value`, `salary`, `net_value`, and
  `discounted_value`.
- Draft pick: `billikenTeam`, `season`, `round`, `expected_pick_in_round`,
  `expected_overall_pick`, `lottery_weighted`, `expected_dollar_value`, and
  `curve_source`.
- Trade target: `my_team`, `partner_team`, `target_player`, `asset_type`,
  `proposed_offer`, `proposed_offer_ids`, `target_v_to_me`, `my_value_delta`,
  `partner_value_delta`, `my_win_now_delta`, `my_future_delta`, and optional
  prospect/pick annotations.

## Evaluation and valuation rules

`/evaluate_trade` uses posture weights from `server.js`:

| Posture | win-now weight | future weight |
| --- | ---: | ---: |
| contender | 1.0 | 0.3 |
| bubble | 0.8 | 0.5 |
| mid | 0.6 | 0.7 |
| rebuild | 0.0 | 1.0 |

Asset IDs are player names or canonical pick IDs. `win_now_value` and
`future_value` are summed for each side, then the requesting team's own
posture weights are applied to what it gives and receives. The response also
computes the partner's net under the partner's distinct posture weights.

## Rebuild checklist

1. Deploy the backend from this repository or reproduce its CSV-to-JSON API.
2. Configure the data-generation job (Railway cron, n8n, GitHub Actions, or a
   scheduler) to run the in-season pipeline and all trade artifacts.
3. Make endpoints private or authenticated if the app will be publicly hosted.
4. Build a React SPA with the three tab flows above. TanStack Query is a good
   fit: cache stable data, refetch standings every five minutes, and use a
   350 ms debounced manual-evaluation mutation.
5. Preserve URL encoding for team names and match backend `billikenTeam`
   identifiers, not only pretty `team_name` values.
6. Test all empty/error/stale states and team names containing spaces.
7. Validate these flows against a live API: all standings, active-only,
   clicking a team, both free-agent types/positions, every selected trade
   partner, loading a suggestion, pick selection, and a manual evaluation.
